# PPT 逻辑框架（Logic）

## 职责边界

决定**表达什么、按什么顺序表达、每页承担什么论点**。不选版式，不做视觉，不改写素材原文。

## 输入

- `ppt-intake` 产出的、已经用户确认的素材台账（含 `M-xxx` 条目）。
- 用户指定的报告类型与用途；未指定时先问一句。

## 第一步：判定大/小报告

| 规格 | 结构 | 适用 |
|---|---|---|
| `large`（大报告） | 封面 + 目录 + 正文 + 附件（附件可选） | 正文超过 2 页，或需要目录导航 |
| `small`（小报告） | 正文 1–2 页，不加封面目录；附件可选 | 正文 1–2 页就能讲完 |

判定规则：

1. 用户明确说「小报告」「一页纸」「单页」→ `small`。
2. 正文要点超过 2 页的承载量 → 自动升级为 `large`，并向用户说明升级原因。
3. 小报告就是大报告正文中某一页的单页复用，不需要单独设计封面和目录。

## 第二步：按报告类型选择逻辑骨架

不同报告类型使用不同的论证结构与页序。先识别类型，再套用对应骨架；用户有明确页序要求时以用户为准。

常见类型的默认骨架：

| 报告类型 | 默认论证结构 | 默认页序 |
|---|---|---|
| 工作汇报 | 结论先行 | 结论 → 关键数据 → 问题与风险 → 下一步 |
| 项目复盘 | 目标—结果—归因—行动 | 目标 → 结果 → 偏差归因 → 经验 → 改进项 |
| 方案提案 | 问题—方案—收益—落地 | 背景与问题 → 方案 → 收益/对比 → 实施计划 |
| 数据分析 | 发现—证据—解释—建议 | 核心发现 → 数据证据 → 原因解释 → 建议 |
| 对外宣讲 | 背景—价值—案例—号召 | 背景 → 价值主张 → 案例 → 行动号召 |

骨架可参数化：章节数、每章页数、哪些页可选，都按素材实际情况调整，不硬套固定页数。

## 第三步：逐页写论点

每个页面条目必须包含：

| 字段 | 含义 |
|---|---|
| `seq` | 页码顺序 |
| `role` | `cover` / `toc` / `chapter` / `content` / `insight` / `appendix` |
| `argument` | 这一页的核心论点，一句话；优先写成行动标题（有主语、有结论） |
| `evidence_ids` | 支撑该论点的素材条目 ID 列表 |
| `page_intent` | 这一页的认知任务：`展示结论` / `对比` / `时间线` / `数据叙事` / `罗列要点` / `流程` / `案例` |
| `source_notes` | 需要标在页面上的来源或口径说明 |

规则：

1. **一页一论点**：一页只承担一个核心结论；两个结论就拆两页。
2. **论点可回指**：`argument` 中的事实性表述必须能在 `evidence_ids` 找到支撑；找不到的，标注为「待确认」，不得自行补全。
3. **Insight 页单独成章**：正文之后如需「启示/建议」页，`role` 设为 `insight`，在目录中单独列出，标题以 `Insight` 开头。
4. **附件页可选**：数据明细、术语表、参考文献放 `appendix`，`large` 和 `small` 都可以有。

## 输出格式

```yaml
report_type: 工作汇报
scale: large
skeleton_id: 工作汇报-结论先行-v1
pages:
  - seq: 1
    role: cover
    argument: "2026 Q3 经营复盘"
    evidence_ids: []
    page_intent: 封面
    source_notes: []
  - seq: 2
    role: toc
    argument: "目录"
    evidence_ids: []
    page_intent: 导航
    source_notes: []
  - seq: 3
    role: content
    argument: "华东区贡献 68% 增量，但增速被华南反超"
    evidence_ids: [M-001, M-007]
    page_intent: 展示结论
    source_notes: ["数据来源：财务系统，2026Q3"]
  - seq: 4
    role: insight
    argument: "Insight：下一季度资源应向华南倾斜"
    evidence_ids: [M-007]
    page_intent: 罗列要点
    source_notes: []
```

## 交互协议

1. 先给出 `scale` 判定和 `skeleton_id`，一句话说明为什么选这个骨架。
2. 以大纲形式展示每页的 `argument` 和 `evidence_ids`，请求用户确认页序和论点。
3. 用户调整页序、增删页、改论点后，只改被指出的部分，不重做整份大纲。
4. 用户确认后才交给 `ppt-layout`。
